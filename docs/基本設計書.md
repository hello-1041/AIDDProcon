# 水切リズム 基本設計書

作成日: 2026-08-11

## 1. 本書の位置づけ

[要件定義書](./要件定義書.md)に基づき、システムの内部構成・画面遷移・データ設計・処理フローを設計する。判定閾値やアニメーションの具体的な数値・座標などのパラメータは、本書では方針のみを示し、詳細設計書で確定する。

## 2. システム構成概要

Vite + TypeScript（Vanilla構成）によるSPA。単一のHTMLページ上に、Canvasによるゲーム画面とDOMによるHUD/UIを重ねて表示する。外部サーバー・バックエンドは持たず、ブラウザ内で完結する。

```
[ブラウザ]
  index.html
    └─ main.ts（エントリポイント／ゲームループ）
         ├─ textalive.ts（TextAlive Player初期化・ビート情報取得）
         ├─ game.ts（ゲーム状態・判定ロジック）
         ├─ render.ts（Canvas描画）
         └─ ui.ts（画面遷移・HUD・DOM操作）
```

## 3. モジュール構成（ディレクトリ設計）

機能別にファイルを分割する方針とする。

| ファイル | 責務 |
|---|---|
| `src/main.ts` | エントリポイント。各モジュールの初期化と、`requestAnimationFrame`によるメインループの起動 |
| `src/textalive.ts` | `textalive-app-api`の`Player`初期化、楽曲再生制御、ビート（拍）情報の取得・提供 |
| `src/game.ts` | ゲーム状態（`GameState`）の保持、クリック時のタイミング判定ロジック、跳躍距離・自己ベストの更新処理 |
| `src/render.ts` | Canvasへの描画（湖・石・波紋・エフェクト等） |
| `src/ui.ts` | 画面（タイトル／プレイ／リザルト）の切り替え、HUD表示、判定結果のテキストポップアップ表示 |
| `src/style.css` | スタイル定義 |

※ 上記は基本設計時点の想定であり、実装を進める中で分割単位を調整する場合がある。

## 4. 画面遷移設計

```
[タイトル画面]
     │ 開始操作
     ▼
[プレイ画面] ──(音楽終了)──▶ [リザルト画面]
     ▲                          │
     │        タイトルに戻る     │
     └──────────────────────────┤
                                 │ もう一度遊ぶ（リトライ）
     ┌───────────────────────────┘
     ▼
[プレイ画面]（同じ楽曲で再挑戦）
```

- **タイトル画面**：開始操作でプレイ画面へ遷移し、楽曲再生を開始する
- **プレイ画面**：音楽終了をトリガーにリザルト画面へ遷移する
- **リザルト画面**：
  - 「もう一度遊ぶ（リトライ）」：同じ楽曲でプレイ画面に戻り、ゲーム状態を初期化して再開する
  - 「タイトルに戻る」：タイトル画面に戻る

## 5. データ設計（ゲーム状態）

ゲーム全体の状態は、単一の`GameState`オブジェクトで一元管理する（クラス分割はせず、`main.ts`のループが状態を読み書きする素直な構成とする）。

```ts
type Screen = "title" | "play" | "result";

type JudgeResult = "just" | "good" | "miss";

interface GameState {
  screen: Screen;              // 現在の画面
  currentDistance: number;     // 現在挑戦中の跳躍距離（石が沈む/音楽終了でリセット）
  bestDistance: number;        // このプレイ内の自己ベスト（最終スコア）
  lastJudge: JudgeResult | null; // 直近の判定結果（HUD表示用）
  isPlaying: boolean;          // 楽曲再生中かどうか
}
```

- `currentDistance`：石が沈む、または音楽が終了するたびに0にリセットする
- `bestDistance`：`currentDistance`が更新されるたびに比較し、上回っていれば更新する
- 判定閾値（Just/Good/Missの境界）や、距離の具体的な計算式は詳細設計書で定義する

## 6. TextAlive連携設計

- `textalive-app-api`の`Player`を、環境構築計画書（[`temp/textalive-app-api-setup-plan.md`](../temp/textalive-app-api-setup-plan.md)）の手順に従いトークン付きで初期化する
- 対象楽曲は固定の1曲を指定する（曲URLは別途選定・確定：TBD）
- 判定の基準タイミングには、TextAliveが提供する**ビート（拍）情報**を用いる
  - 再生中の現在位置（`player.timer.position`相当）に対し、直前・直後のビートタイミングを参照し、クリック時刻との差分（ズレ幅）を算出する
  - 具体的な取得方法（該当API・プロパティ名）は、実装時にAPIリファレンスで確認し詳細設計書に反映する（TBD）
- `onVideoReady`等のライフサイクルイベントを利用し、ビート情報の取得可能タイミングを制御する

## 7. 判定ロジック設計

- **受付方式**：常時受付方式とする。プレイヤーはいつでもクリックでき、クリック時刻に最も近い基準ビートとの差分（ズレ幅）を評価する（1拍ごとに待ち構えるキュー方式は採らない）
- **判定段階**：3段階（Just／Good／Miss）とする
  - ズレ幅が小さいほどJustに近い判定となり、一定以上大きい場合はMissとする
  - 各段階の具体的な閾値（ms）は詳細設計書で確定する（TBD）
- **距離算出**：ズレ幅に応じて連続的に変化する方式（線形減衰等）とする。ジャストタイミングに近いほど、その回の跳躍で加算される距離が大きくなる。具体的な計算式は詳細設計書で確定する（TBD）
- **Miss時の挙動**：
  1. Miss判定となった時点で、その挑戦を終了（石が沈む）
  2. `currentDistance`と`bestDistance`を比較し、上回っていれば`bestDistance`を更新
  3. `currentDistance`を0にリセットし、直後に新しい石を投げて次の挑戦を開始する
- **音楽終了時の挙動**：進行中の挑戦を終了し、上記2と同様に`bestDistance`を確定した上でリザルト画面へ遷移する

## 8. 描画設計（Canvas）

- 描画レイヤーは背景（湖面）→波紋・水しぶきエフェクト→石、の順に重ねて描画する
- HUD（現在の跳躍距離・自己ベスト・判定結果ポップアップ）はCanvas上またはDOM要素のいずれで表示するかを含め、具体的なレイアウト・座標系・画面リサイズ対応は詳細設計書で確定する（TBD）
- アニメーションは`requestAnimationFrame`によるメインループ内で、毎フレーム状態を参照して再描画する

## 9. UI・フィードバック設計

- **プレイ中HUD**：現在の跳躍距離、自己ベストをリアルタイム表示する
- **判定結果のフィードバック**：クリックのたびに、テキストポップアップ（「Just!」「Good」「Miss」等）表示と、石の挙動変化（跳ね方・エフェクトの違い）の両方で判定結果を表現する
- **リザルト画面**：最終スコア（自己ベスト）、「もう一度遊ぶ」ボタン、「タイトルに戻る」ボタンを表示する

## 10. 状態管理方針

- ゲーム全体を単一の`GameState`オブジェクトで保持し、`main.ts`内の`requestAnimationFrame`によるメインループが、毎フレーム「状態更新（判定・時間経過処理）→描画（`render.ts`）→UI反映（`ui.ts`）」を行う一元管理構成とする
- 画面（タイトル／プレイ／リザルト）ごとのクラス分割は行わず、`GameState.screen`の値に応じて処理・描画を分岐させるシンプルな構成とする
